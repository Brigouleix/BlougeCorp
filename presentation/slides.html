Contexte & Problématique
Pourquoi BlougeCorp existe

🎯 Problème identifié

Organiser un voyage en groupe est complexe : choisir la destination, comparer les prix, coordonner les membres, gérer les invitations et planifier l'itinéraire demande de nombreux outils disparates.

💡 Solution proposée

Une plateforme web centralisée permettant à un groupe d'amis ou de collègues de proposer, voter, commenter et planifier des destinations de voyage en temps réel.

👥 Cible utilisateur

Groupes de 2 à 20 personnes souhaitant organiser des voyages collectifs : amis, famille, collègues, associations.

Flux utilisateur type
Créer un groupeNommer, illustrer, inviter par email
Proposer des destinationsAvec images, prix, dates, carte
Commenter & noterÉchange d'avis entre membres
Créer le Road TripOrdonnancer les étapes, budget total
Partager les photosGalerie de groupe partagée
02
Fonctionnalités Principales
Vue d'ensemble des modules applicatifs

🔐 Authentification

Inscription, connexion JWT, mot de passe oublié avec token email, changement de mot de passe, suppression de compte.

👥 Gestion de Groupes

Création avec image, invitation par email (PHPMailer), gestion des membres, suppression par le créateur.

📍 Destinations

Ajout avec géolocalisation Leaflet/Nominatim, prix hébergement + transport, dates, archivage, suppression.

💬 Commentaires & Notes

Système de commentaires avec note /5 par destination. Calcul de note moyenne affichée sur chaque carte.

🗺️ Road Trip

Sélection et ordonnancement de destinations, calcul automatique du budget total, export PDF de l'itinéraire.

📸 Galerie Photos

Upload de photos par les membres du groupe (base64), légende, affichage en galerie partagée.

🌐 Multi-langues

Interface disponible en 7 langues : Français, Anglais, Espagnol, Allemand, Italien, Portugais, Japonais.

🗄️ Archive

Les destinations peuvent être archivées (soft delete) puis restaurées ou supprimées définitivement.

🛡️ Admin Dashboard

Statistiques globales, gestion des utilisateurs/groupes/destinations, test SMTP en temps réel.

07
Sécurité
Authentification, autorisation et protection des données

🔑 JWT HS256

Tokens signés côté serveur. Payload contient id, username, email, isAdmin. Vérification systématique à chaque requête protégée.

🔒 BCrypt

password_hash() avec PASSWORD_BCRYPT. Vérification via password_verify(). Aucun mot de passe en clair en BDD.

💉 Anti-injection SQL

100% des requêtes utilisent des prepared statements PDO avec paramètres bindés. Zéro concaténation SQL.

🔐 CORS configuré

Origines explicitement autorisées, headers listés, méthode OPTIONS gérée pour les requêtes préflight.

🛡️ Vérification des rôles

Créateur groupe, proposeur destination, admin : chaque action vérifie le rôle côté serveur depuis le JWT.

⏱️ Token expirable

Reset password : token 32 octets cryptographiquement sûr, durée de vie 1h, invalidé après usage unique.

🛡️ Admin server-side

Le rôle admin n'est accordé que si l'email du JWT correspond à l'email admin défini dans la config serveur.

🖼️ Images base64

Stockage en TEXT en BDD. Pas de fichiers physiques, pas de path traversal possible, pas de MIME spoofing.

08
Système d'Emails
PHPMailer · Brevo SMTP · Invitations + Reset mot de passe

📧 Invitation à un groupe

Email HTML avec nom du groupe, boutons "S'inscrire" et "Se connecter" pointant vers APP_URL. Envoyé pour chaque email saisi par le créateur.

🔑 Réinitialisation mot de passe

Email HTML avec lien tokenisé (APP_URL/reset-password?token=…). Token 32 octets, expiration 1h, usage unique.

🧪 Test SMTP admin

Endpoint POST /api/admin/test-email permet de vérifier la configuration SMTP en direct depuis le dashboard admin sans avoir à déclencher une vraie action.

Configuration .env
# Brevo SMTP (recommandé) MAIL_HOST=smtp-relay.brevo.com MAIL_PORT=587 MAIL_USERNAME=votre@email.com MAIL_PASSWORD=clé_SMTP_Brevo MAIL_FROM=noreply@yourdomain.com # URL de l'application APP_URL=http://localhost:3000
Pourquoi Brevo ?
Tier gratuit 300 emails/jour · SMTP TLS 587 · SPF/DKIM configurables · Pas besoin de domaine custom pour tester
Alternative : Gmail App Password
smtp.gmail.com:587 avec mot de passe application (2FA requis). 500 emails/jour.

Accès sécurisé
🔐 Côté Frontend
1. Lecture du token JWT dans localStorage
2. Décodage du payload
3. Vérification que email === email admin
4. Redirection vers /my-groups sinon
🛡️ Côté Backend
1. JWT::getUserFromRequest()
2. Comparaison email avec ADMIN_EMAIL défini server-side
3. Retour 403 si non admin
→ Double vérification : UI + API
⚠️ Principe de moindre privilège
Même si le frontend est contourné, le backend refuse systématiquement les requêtes admin sans le bon email dans le JWT.
